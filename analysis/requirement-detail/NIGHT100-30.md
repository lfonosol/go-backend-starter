# NIGHT100-30 — Run the verification loop

> "An unattended run is a verification loop: one agent runs the GSD automated process for a phase, a second agent checks that work, and the failures it finds are reassigned. The loop exits when everything passes, and is bounded either by five attempts or by only documentation or low-level issues remaining."

MoSCoW and Status live in the shared Scope Tracker sheet, and the requirement's phase in `.planning/ROADMAP.md` — **look them up there; this card does not restate them.** The quotes below are the workshop-corpus record.

**Sources:** change record `CR-110` · locus `S-02 how overnight mode terminates` and `S-01 25:42`

## What this is for

An unattended run with nobody checking it produces work nobody has looked at. This requirement puts the checking inside the run: a second agent reviews the first agent's output and sends back what fails, repeatedly, until there is nothing left worth sending back. That is what makes the night's output something the morning can start from rather than something the morning has to audit from scratch. The two bounds exist so the loop cannot run forever on a problem it will never solve, wasting a night on one stuck task.

## The evidence

**What the source says.**

> "Overnight mode uses the GSD automated process. An agent launches a sub-agent to do the work, and that agent then double-checks the work. Where there are issues it reassigns them. That creates a loop — one agent running the process, another confirming it is fine — and as soon as everything passes, the loop exits. So it is not a count. I would want it to be a combination of chances and severity. Three is too little; move it to five. And stop when only documentation or low-level issues are left."
> — the practitioner, `workshop-docs/practitioner-notes-2026-09-19.md` § *Capture — how overnight mode terminates*

> "Day one, we can first get the automation there, put some really strict rules. Okay, you have three chances to try and run this."
> — the delivery lead, `S-01 25:38`–`25:42`

**Both loci stand, and the reason is stated rather than assumed.** The notes carry the loop and the two exit conditions. The transcript is the origin of the requirement that the run be bounded at all, and **its count of three is superseded by the five** — a planner who reads the transcript alone will otherwise build the wrong bound.

**The reasoning on the register.** The run terminates on a judgment about what is left, not on a tally of tries. **Two bounds stand and either one is sufficient.**

**Judgment calls that bear on it.** When the row was rewritten to the practitioner's redefinition, the RAID assumption behind it was **replaced in place rather than deleted and re-minted**, because its subject is unchanged: an unmeasured bound on the unattended run. The alternative was stated so the choice reads as a decision and not a default. The row's step name was also changed, because the old one no longer described it.

## Open items and watch-outs

- **The second bound is not checkable at all today.** "Only documentation and low-level issues remain" needs a severity classification the harness does not have. Without one, shipping this requirement ships the five-attempt bound alone.
- **Neither bound is measured.** Five is a stated value. Too low and the loop ends with real work unfinished; too high and a stuck loop burns a night. Build the bound as a value that can be changed, and record what the first runs actually needed.
- The severity vocabulary this needs is the same one the morning ranking needs. Deciding it once, here, is the cheaper order.
