# SITE100-40 — Mark each content area

> "Each content area is marked either as progressive-reveal or as human-facing, and that marking is recorded with the area."

MoSCoW and Status live in the shared Scope Tracker sheet, and the requirement's phase in `.planning/ROADMAP.md` — **look them up there; this card does not restate them.** The quotes below are the workshop-corpus record.

**Sources:** change record `CR-050` · locus `S-02 capture`

## What this is for

A decision that lives only in someone's head cannot be built on and cannot be checked. This requirement turns the clean-up pass's per-area judgment into a recorded fact that sits beside the area itself, in the same configuration that defines the area, so the two cannot drift apart. It is what makes progressive reveal buildable at all: without it the reveal has no input and there is nothing to say which pages get it. For a reader it changes nothing directly; for anyone maintaining the site afterwards it is the difference between a rule and a habit.

## The evidence

**What the source says.** The same capture passage that carries the clean-up pass carries this: *"identify for each content area how we want to organize it, which gets the progressive reveal and which is for the humans to consume."* The full passage is quoted on [SITE100-20](SITE100-20.md).

**The reasoning on the register.** **The marking is what makes progressive reveal buildable: without it the reveal has no input.** It is decided during the clean-up pass and recorded by this row. It adds a marking field to each navigation and roadmap-section entry in the board's configuration, read by the docs module — **so the marking is held beside the area itself.**

**Judgment calls that bear on it.** **This row was migrated from the prototype register when that sheet was dropped**, because no prototype was reviewed on this engagement. Four other rows were migrated with it. **The retired prototype identifier it replaces is recorded in the provenance note and is deliberately not written into the register itself** — a shipped register does not cite a register that does not exist. A planner should not go looking for a prototype record; there is none, and its absence is a decision.

**Glossary terms in play.** *Progressive reveal*. *Role-based view*.

## Open items and watch-outs

- **The rule admits two values and nothing else.** If an area turns out to need both, the field is a pair rather than a binary and this requirement's shape changes. That is settled during the clean-up pass, not here.
- The marking has to be held with the area rather than in a separate list, or the two drift and the site says one thing while the configuration says another.
